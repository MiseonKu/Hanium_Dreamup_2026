# Target-Plan Audit: `target_plan_3d_random_n50_v3.json` (2026-08-05)

> **The v3 plan this audits is superseded — do not run it as-is.** (Note
> added later the same day.) The audit findings below are unchanged and
> correct *about v3*: it really does have 50 points, 0 duplicates, 0
> joint-limit violations. But v3 was generated on two convention errors
> found afterwards — `logical_deg` treated as a physical angle, and an
> L-shaped reference pose instead of the real straight one. The symptom is
> visible in this document's own output: `logical_deg axis[1] range:
> [10.16, 45.17]` confines shoulder_lift to the low end of its 5–154 label
> range — the "arm never comes up" problem. See
> `docs/FK_CONVENTION_CORRECTION.md`; `generate_3d_points_v5.py` is the
> corrected generator. Kept as the record of what segment 012 actually ran.

`docs/TARGET_WORKSPACE_FRONT_120.md` documents this package's own generator
(`tools/generate_front_120_target_plan.py`, CSV+metadata output, `front_120`
2D-azimuth-sweep mode only). This document covers a **different** plan file
that real hardware actually ran: `sessions/real_motion_demo/
target_plan_3d_random_n50_v3.json`, driving the real segment 012 50-point
sweep. Confirmed by exact match of the recorded `logical_deg` for `T000`'s
settled encoder sample (`[48.3, 14.4, 92.6]`) against this plan's `T000`
(`[48.26, 15.19, 92.51]`) -- the other candidate plans in the same directory
(`target_plan_3d_random_n50.json`, `_v2.json`) share the same `T000`-`T049`
id scheme but very different `logical_deg` values for `T000`, so id overlap
alone does not identify which plan drove a segment; the recorded joint
angles do.

## The reproducibility gap

`target_plan_3d_random_n50_v3.json` was generated by
`experiment_scripts/generate_3d_points_50_v3.py`, an ad hoc script, **not**
by `tools/generate_front_120_target_plan.py`. Its docstring explains why:
v1/v2 (independent-uniform joint-space sampling, take-first-N) produced an
uneven, banded Cartesian distribution -- joint-space-uniform is not
Cartesian-uniform for this 2-link revolute chain. v3 fixes this with a
4000-candidate pool + greedy farthest-point sampling (FPS) in Cartesian
space to select 50 points with even spatial coverage. This is a real
capability the official generator does not have: `tools/
generate_front_120_target_plan.py` is a thin wrapper with **zero generation
logic of its own** (by design, per its own docstring) -- it forwards to
`02_FK_IK/scripts/
generate_pre_imu_targets.py`'s bin-balanced-sampling pipeline, a
structurally different approach (classify into radial/azimuth/height/
bending/posture bins, then sample bin-balanced), and outputs CSV+metadata,
not this plan's flat-JSON `{target_id, planned_order_index, q_rad,
p_xyz_mm, logical_deg, workspace_mode}` shape.

**Decision: extend the audit tool, don't port FPS into the 08 wrapper.**
Porting farthest-point sampling into `tools/generate_front_120_target_plan.py`
would mean putting real generation logic into a file whose entire design
premise (stated in its own docstring) is "no generation logic lives here."
The only way to add FPS "cleanly" per this package's own architecture would
be to add it as a new mode inside `03_flexible_link_fkik_workspace_point_
algorithm/workspace_points/pre_imu_targets.py` -- the actual home of every
existing sampling mode -- which is real, non-trivial new algorithm work in
a different package, out of scope for an audit-tooling pass. So this task
did the safer, still-fully-in-scope half of the ask: `tools/
audit_target_plan.py` now has a second mode (`audit_json_plan()` /
`--plan-json`) that correctly audits the v3 plan's actual JSON shape, so
the plan that real hardware actually ran is no longer un-auditable. If a
single canonical generator is wanted going forward, the recommendation is:
port FPS into `workspace_points/pre_imu_targets.py` as a new sampling mode
alongside its existing bin-balanced approach (where the rest of the
generation logic already lives), not into either package's CLI wrapper.

**Notes on the numbers:**
- Joint limits re-checked against `03_flexible_link_fkik_workspace_point_
  algorithm/config/robot_config.yaml`'s `joint_limits_rad`, using
  `fkik.geometry.within_joint_limits(q, config, margin=0.05)` -- the exact
  call and margin `generate_3d_points_50_v3.py` itself used
  (`MIN_JOINT_MARGIN_RAD = 0.05`). Zero violations, as expected: the
  generator already filtered candidates against this same check.
- Azimuth range `[-59.63, 59.98]` deg is close to, but not exactly, the
  named `front_120` sector's `±60°` bound -- expected, since this plan's 50
  points are FPS-selected from a 4000-candidate pool already gated near
  that boundary, not a fresh regeneration against the `front_120` config.
- This 3-axis pipeline (`q1`/`q2`/`q3` = base yaw / shoulder pitch / elbow
  pitch) intentionally excludes `wrist_roll`/`gripper` -- see
  `docs/THREE_AXIS_EXPERIMENT_SCOPE.md` for the scope decision this task
  did not duplicate.
- 3-way joint-limit consistency check (didn't move the numbers, but worth
  recording): re-running with `margin=0.0` also produces zero violations,
  so the result isn't margin-sensitive at this candidate set.

## Why no plot

`requirements.txt` does not list `matplotlib` (confirmed by reading it --
only `pyserial`, `pytest`, `PyYAML`). `experiment_scripts/plot_points.py`
does use matplotlib but lives in `experiment_scripts/`, outside this
package's declared dependencies. `audit_json_plan()`'s coverage summary
(XYZ range + azimuth histogram-as-text, shown above) is deliberately
matplotlib-free so it runs with this package's existing dependency set.
